# Observe synthetic archive costs locally

This optional tool measures invented data, never an existing personal archive.
It helps compare operations and code versions on the same machine. Observations
are not a performance score, acceptance threshold, cross-machine comparison or
large-archive speed guarantee. No public timing benchmark is claimed.

## Reproducible input, local observations

Create an empty directory named OUTPUT outside this checkout and replace the
literal placeholder below. The generator creates a new child directory and only
fictional messages. The runner creates another new child directory, its own
archives, and an exclusively new private receipt:

```sh
python examples/make_scale_fixture.py OUTPUT/scale-fixture --conversations 50 --messages 2 --seed 7
python benchmark.py OUTPUT/scale-fixture --work-dir OUTPUT/scale-work --output OUTPUT/scale-receipt.json --repetitions 1
```

Do not substitute an existing archive. The runner accepts only files that exactly
match regenerated bytes from the bounded integer fixture parameters, not merely
a manifest saying `synthetic_only`. It checks the manifest and file hashes. Fixed
ZIP timestamps, LF serialization and hash-derived text variation make the same
parameters reproduce the same input bytes. A supplied directory is not proof of
authorship or permission; this byte check only identifies this synthetic recipe.

The receipt contains private local runtime information and measurements. Keep it
outside public repositories. stdout reports counts, not measured times or runtime
versions. Neither tool calls a model or network, discovers private inputs, or
imports source files other than the explicitly selected synthetic fixture.

## What is measured

Time and Python allocation peaks are measured in separate executions. Tracing
changes timing, so traced runs must not be interpreted as timing samples.
Repetitions are explicit. OS and SQLite caches are not flushed or controlled;
these are not cold-cache measurements. Python tracemalloc does not include SQLite
native allocations, operating-system cache, total process RSS or all storage I/O.

The fixture covers web, local-codex and normalized imports, with synthetic local
title revisions and review decisions applied through the regular APIs. The runner
observes title/body/missing literal searches, FTS search, list offset pages, show,
review queues, title history, check-import, export inventory, ZIP inventory and
preparation, and recovery declaration/rehearsal. Write operations get fresh output
paths. Import counts, conflict checks, recovery success and intermediate staging
cleanup are checked after measuring; a result-level failure aborts instead of
recording its potentially faster failure path as a normal operation. These are
functional gates, not performance thresholds. Timing excludes fixture construction and common archive setup unless the
named operation is itself an import. No PASS/FAIL performance threshold is used.

The private receipt binds the fixture manifest and implementation identity,
including the release label and hashes of library and benchmark source files.
A matching identity identifies bytes, not an approval or correctness guarantee.
Measurements can change between repetitions on unchanged code. Compare the same
recipe and operation before attributing a difference to a code change.

## Cost map, not a speed promise

| Operation | Work that remains |
|---|---|
| Adapter import | Entire input parsing, rows and derived normalized bytes remain in memory; one redundant JSON decode was removed. SQLite still checks each message identity and writes its index and ledgers. |
| Normalized ingest | Reads one complete immutable byte snapshot, validates all records and incoming conflicts, then writes the selected archive. |
| Literal `find` | Casefolded substring scans preserve semantics; no tokenized FTS prefilter is substituted. A small result page does not imply small input work. |
| FTS `search` | Uses the FTS index; results have token-query semantics, not literal substring equivalence. |
| `list`, `show`, review queues | Output can be bounded or paged, while inventories, title-history lookups, source-wide checks and sorting can still process much more data. |
| Title history | Counts and reads matching history; repeated title revisions affect cost. |
| `check-import`, `list-export` | Parse the chosen input; pagination does not make source parsing incremental. |
| ZIP inspect/prepare | Current fixed archive/member/entry limits still apply; the full ZIP snapshot is retained. Preparation validates a selected member before publishing it. |
| Recovery declaration/rehearsal | Reads and compares declared logical rows/index checks; not a constant-memory or constant-time backup operation. |

Counts allow 1..50,000 conversations and 1..1,000 messages per conversation,
with at most 50,000 messages in total and an additional 64 MiB fixture-byte bound.
A conservative construction budget may reject a combination before the final
byte total is built. Seeds are integers 0..4,294,967,295; repetitions are 1..5.
These limits are safety limits, not statements that every size
will be fast or fit the user's available memory. Increase sizes deliberately in
separate new directories. This release does not raise ZIP limits, change the
one-snapshot contract or implement streaming. The lazy title-history index below
changes lookup cost only after an explicit title write.

## Lazy title-history index: synthetic observation

An explicit title write creates `title_history_identity` on
`title_history(source,conversation,id)` inside its existing transaction if absent.
Read-only commands leave older archives untouched. A conflicting existing index
name is preserved, not repaired; the optimization is not guaranteed in that case.
There is no archive-version prerequisite, new row format or automatic migration.
The index adds storage and write-maintenance cost and does not make inventories,
source-wide checks, sorting or literal substring scans bounded.

A deterministic seed-43 fixture with 1,000 conversations, 4,000 messages, 1,500
title-history rows and 500 review-history rows was measured before and after this
change, using three repetitions per operation and separate traced-memory runs.
The ratio of before/after median elapsed time in this local observation was:

| Operation | Before / after median |
| --- | ---: |
| Plain review queue | 18.9 |
| Unrenamed review queue | 107.2 |
| Review-state filter | 6.2 |
| Offset conversation list | 1.9 |
| Title history | 1.3 |

The synthetic archive grew from 3,670,016 to 3,735,552 bytes (65,536 bytes).
Tests also inspect the actual reader SQL with `EXPLAIN QUERY PLAN`, verifying
index use for all four title-history lookup shapes and identical logical rows,
reader results and recovery digests. Stale/unknown targets and injected failures
leave no newly committed index or history row; same-name conflicting indexes
remain unchanged.

These ratios are observations from one environment, not a public timing benchmark,
performance threshold or prediction for another archive. Cache state was not
controlled. Absolute timings and runtime identity remain in private synthetic
receipts. Queries, data distribution, index availability and write costs matter;
no speedup is promised, including for operations not targeted by this index.

## Failure and retention boundary

Existing output files or directories are refused, including dangling symlinks.
A failure after creating a new directory can leave partial synthetic files or
working archives. Nothing is silently deleted, replaced, resumed or repaired;
inspect the new scratch directory and use fresh paths for another run. A missing
final receipt does not imply that no work directory was created. Receipt publication
uses the existing exclusive no-overwrite publication boundary. If intermediate
staging cleanup fails, the run stops with the published scratch files retained.
If the final receipt was published but staging cleanup fails, stdout explicitly
reports `receipt_published: true`, `staging_cleanup_complete: false` and the
generated staging basename. Inspect that remainder in the receipt directory; do
not retry against the already-published receipt path.

These measurements establish neither private archive completeness, recovery
readiness, retention, rights, consent nor suitability for a particular machine.
Existing import receipts, queries and source/provenance meanings are unchanged.
